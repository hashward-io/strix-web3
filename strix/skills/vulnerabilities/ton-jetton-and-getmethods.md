# TON Jettons and Get-Methods

Jettons deliver funds through a `transfer_notification` message whose *header* sender is a jetton wallet and whose *body* carries the original sender and amount. Get-methods are read-only conveniences that off-chain clients trust; mistaking either for on-chain authority loses funds or lets an attacker mint credit.

## Where to look

- Jetton notification handling: op `transfer_notification` (`0x7362d09c`) in `recv_internal`, Tact `receive(msg: JettonTransferNotification)`. Fields: `query_id`, `amount`, `sender` (the original owner), `forward_payload`.
- Sender validation: is the contract checking that the *header* `src` equals the expected jetton wallet, and that the wallet belongs to the expected master?
- Master checks: a stored `jetton_master` address compared against the wallet's `get_wallet_data` / state init, or against the `master` field of the notification.
- Derivation: `get_wallet_address(owner)`, and the canonical wallet address `hash(state_init(code, master, owner))`.
- Get-methods: `get_wallet_data`, `get_jetton_data`, `get_wallet_address`, and any Tact `get fun`.
- Idempotency: `query_id` uniqueness and any dedup of notifications.
- Tact lifecycle: `init()`, `init(owner)`, and whether a normal `receive()` can re-run init logic.

## Attack plan

1. Deploy a fake jetton wallet that sends a `transfer_notification` with an inflated `amount` and a `sender` set to a victim or a trusted address. If the contract credits on the body's `amount`/`sender` without verifying the header `src`, it credits free balance.
2. Confirm the check is `equal_slices(src, expected_wallet)` where `expected_wallet` is derived from `(master, this_contract)` — not a body-supplied address and not a stale cached value.
3. Master confusion: if the contract accepts a notification from *any* wallet that reports a trusted `master`, an attacker deploys a look-alike master/wallet pair whose getters return the trusted master address. Validate by deriving the wallet from the master's known code and state init.
4. Get-method assumptions: anything a keeper, frontend, or sibling contract reads via a get-method (`get_wallet_address`, balances) can be spoofed if the caller trusts the returned value across a trust boundary. Get-methods cannot be called from on-chain contract logic and carry no caller identity — never treat them as authorization.
5. `query_id` reuse: replay a previously accepted notification (same or colliding `query_id`) if the contract does not dedup. Notifications are internal messages and can be re-generated by anyone who controls a wallet that can target the contract.
6. `get_wallet_address` derivation mismatch: if the contract computes the expected wallet with a different formula (missing workchain, wrong code hash, wrong owner) than the actual jetton implementation, the check either always fails (DoS) or accepts a wrong wallet.
7. Tact `init()` re-entry: a public message that re-runs initialization (e.g. an `init` message, or a `receive` that does not guard state) can reset owner/params on a live contract.

## Proof

- Sandbox PoC (`@ton/sandbox`, `npx blueprint test`): deploy a malicious jetton wallet, invoke the contract's notification handler, and show credited balance with no real transfer.
- Or replay an identical notification and show double-crediting.
- For derivation, print the expected wallet address from the contract's formula and from `get_wallet_address` on the real master and diff them.

## Fix

- Credit only when the header `src` equals the wallet derived from the expected master and this contract's address.
- Verify the master through the wallet's own state / `get_wallet_data`, not a body field.
- Treat get-methods as untrusted, off-chain signals; never gate on-chain authority on them.
- Dedup notifications by `query_id`, and treat `sender` in the body as informational (the true fund source is the wallet).
- Make `init()` run only at deployment; guard any live re-initialization behind owner authority.

## Message fields to verify

- The jetton wallet `transfer_notification` op is `0x7362d09c`; its `sender` field is the original owner, not the wallet.
- The wallet's authoritative data is its **state** (`get_wallet_data` returns `(balance, owner, jetton_master, wallet_code)`); the getter is a convenience, not a source of on-chain truth.
- The canonical wallet address is `hash(state_init(wallet_code, jetton_master, owner))` — recompute it with the expected code and master.
- `forward_ton_amount` and `forward_payload` are attacker-influenced and must never drive value or authorization.

## Severity and finding bar

- Crediting balance from an unverified notification is **Critical** (mint from nothing).
- A derivation mismatch that accepts the wrong wallet is **High**; one that rejects the right wallet (DoS) is **Medium**.
- Get-method trust across a value boundary is **High**; cosmetic or off-chain-only use is **Low**.
