Skills are structured knowledge packages that give Strix Web3 agents deep expertise in specific bug classes, protocol types, and audit techniques.

## The Idea

LLMs have broad but shallow smart-contract security knowledge. They know _about_ reentrancy, but lack the nuanced judgement an experienced auditor uses — which callbacks matter, how rounding direction compounds, how an oracle's decimals really flow through a share price.

Skills inject this deep, specialized knowledge directly into the agent's context, turning a generalist into a specialist for the task at hand.

## How They Work

When Strix Web3 spawns an agent for a subsystem or a bug class, it selects up to 5 relevant skills based on the context:

```python
# Agent created to audit the vault automatically loads the relevant skills
create_agent(
    task="Audit the ERC-4626 vault share math and oracle reads",
    skills=["vaults-erc4626", "precision-rounding", "oracle-manipulation"],
)
```

The skills are injected into the agent's system prompt, giving it access to:

- **Attack lenses** — The twelve Pashov lenses, each a way of looking at the code
- **Bug-class playbooks** — How each class manifests, and the code shapes that carry it
- **Validation methods** — How to confirm a finding and avoid false positives

## Skill Categories

### Attack Lenses (`hacking_agents/`)

The twelve lenses, applied in parallel across the protocol's subsystems.

| Skill               | Coverage                                                     |
| ------------------- | ------------------------------------------------------------ |
| `math-precision`    | Rounding direction, precision loss, decimal/scale mixing     |
| `access-control`    | Role boundaries, missing modifiers, initialization           |
| `economic-security` | Incentive and economic design flaws, griefing                |
| `execution-trace`   | End-to-end execution trace reasoning, call graphs            |
| `invariant`         | Deriving and challenging the protocol's invariants           |
| `periphery`         | Contracts that touch the core, integrations and adapters     |
| `first-principles`  | Reason from the spec, not the implementation                  |
| `asymmetry`         | Where one party has information or power the other lacks      |
| `boundary`          | Edges, zero/one/total-supply, first/last actor                |
| `numerical-gap`     | Dimensional analysis, scale mismatches, overflow             |
| `trust-gap`         | Who is trusted, and what happens when trust breaks           |
| `flow-gap`          | Where value enters, moves, and can get stuck                 |

Internal categories (`scan_modes/`, `coordination/`, `analysis/`) are selected by the runtime, not by users.

## Skill Structure

Each skill is a Markdown file with YAML frontmatter for metadata:

```markdown
---
name: skill_name
description: Brief description of the skill's coverage
---

# Skill Title

Key insight about this bug class or technique.

## Attack Surface
What this skill covers and where to look.

## Methodology
Step-by-step audit approach.

## Techniques
Concrete code shapes and the failure they enable.

## Validation
How to confirm a finding and avoid false positives.
```

## Contributing Skills

Contributions are welcome. Add a `.md` file in the appropriate category with YAML frontmatter (`name` and `description`). Good skills include:

1. **Real-world patterns** — Code shapes seen in production protocols
2. **Concrete examples** — Minimal vulnerable snippets and their fix
3. **Validation steps** — How to prove it with a test or a trace
4. **Protocol awareness** — Where the pattern commonly appears
